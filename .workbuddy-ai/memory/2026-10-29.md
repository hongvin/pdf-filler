## Removed the Basic-auth gate; Cloudflare Access takes over

The user asked to "remove the sign in" and then added "i will use cloudflare
access to guard them". The Basic auth middleware was deleted rather than
disabled.

- Deleted `functions/_middleware.js` (recoverable from git:
  `git show 022c93b:functions/_middleware.js`).
- `functions/api/config.js`: dropped the `if (!env.APP_PASSWORD) → 503` guard.
  It existed only to back up the middleware, and with the middleware gone it
  would have made the endpoint depend on a variable nobody uses any more.
  The hardening headers (`no-store`, `nosniff`, `referrer-policy`,
  `x-robots-tag: noindex`) stayed — they are set in the local `json()` helper
  and do not come from `public/_headers`, which never applied to Functions
  responses.
- `wrangler.toml`: removed `APP_USER` from `[vars]`. Left the `APP_PASSWORD`
  secret in place (harmless, and makes restoring the gate a one-file job).
- README: structure tree, config table, "About the access gate", local dev.

Verified: `wrangler pages dev` → `/` 200, `/api/config` 200 with the values,
no credentials. Deployed to https://pdf-filler-7ju.pages.dev, then a real
browser showed `config loaded` and no login prompt.

### Access cannot protect *.pages.dev

This is the part worth remembering. Cloudflare's own docs for a self-hosted
Access app say: "Domains must belong to an active zone in your Cloudflare
account." `pdf-filler-7ju.pages.dev` is not in the user's zone, so it **cannot**
be an Access application domain. The user must attach a custom domain to the
Pages project and put Access on that.

Which means: until the custom domain exists and `pages.dev` is blocked, the
deployed site is genuinely open, `/api/config` included. `x-robots-tag` is not
a control. If the user asks again, the next step is a host-check middleware
(404 when `Host` is not the canonical domain), not another password.

## Migrated Pages → Workers (same day, later)

The user asked why `pdf-filler-7ju.pages.dev` was still reachable and whether
it could be a Worker instead. Both parts answered by the same fact:

- A Pages project **always** gets `<project>.pages.dev`. It cannot be removed or
  renamed, and it **cannot be an Access application domain** — Access domains
  must belong to a zone on the account, and `pages.dev` is Cloudflare's zone.
- A Worker's `workers.dev` route **can** be disabled (`workers_dev = false`) and
  **can** be gated with Access directly: Settings → Domains & Routes →
  workers.dev → Enable Cloudflare Access. No custom domain required.

So the app now runs on Workers Static Assets.

- New `worker.js`: `/api/config` (GET/HEAD only, 405 otherwise), 404 for other
  `/api/*`, everything else through `env.ASSETS.fetch()`. Security headers are
  re-applied in code to every response — `_headers` is a Pages convention and
  should not be trusted to survive the move.
- `wrangler.toml`: `main = "worker.js"`, `[assets] directory = "./public"`,
  `binding = "ASSETS"`, `run_worker_first = true` (so headers apply to static
  files too), `pages_build_output_dir` removed.
- `functions/` deleted — Pages-only. Git history keeps it.
- `BIDDER_IC` re-created as a **Worker** secret (`wrangler secret put`); Pages
  secrets do not carry over. Piped from `.dev.vars` so it was never printed.
- Deployed to https://pdf-filler.hongvin.workers.dev.

Verified locally and live: `/` 200, `/api/config` 200 with the IC, unknown
`/api/*` 404, `POST /api/config` 405, all 18 assets 200, headers present,
browser boot shows `config loaded` + stamp thumbnail + zero errors.

### The Pages project is still live

`pdf-filler-7ju.pages.dev` was **not** removed by the migration — it still
serves the last Pages build and is not covered by Access. The user has to
delete that project (or repoint it) for the old URL to stop working. Do not
assume `wrangler deploy` retired it.
