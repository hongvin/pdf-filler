Read the whole deployed surface (`public/app.js`, `public/lib/*.js`,
`functions/*.js`, `index.html`, `styles.css`, `wrangler.toml`, `README.md`) and
ran the headless harness against the real template + both fixtures. Harness is

to `node_modules`; pdf-lib 1.17.1.

### Confirmed bug (verified with a hand-built PDF, fix proven)

`detect.js:findUnderlines` never sees rules drawn with the PDF **`re`
operator**. pdf.js emits those as `OPS.constructPath` with a *command list* of
`[OPS.rectangle]`, but the command loop (detect.js:220-236) has no `rectangle`
case and hits `else { break; }`. The separate top-level
`else if (fn === OPS.rectangle …)` branch at detect.js:243 is **dead code** —
pdf.js never emits `OPS.rectangle` as its own op (grepped the bundle: the only
occurrence is inside the canvas renderer's constructPath switch).

Measured: a document with `160 698 340 1 re f` rules and correct labels yields
**0 blanks** with the current code, **2 correct blanks** once the command loop
handles `OPS.rectangle` (push both long edges, `ci += 4`). Word / LibreOffice /
Acrobat all emit rules this way, so this is the common case, not an edge case.
Note pdf-lib's own `drawRectangle` emits moveTo/lineTo/closePath, which is why
the existing `fixture-underline.pdf` passes and hides the bug.

## All findings fixed, verified in a real browser (same day, later)

Every item above is now fixed. Details worth keeping:

- **`re` operator** — added an `OPS.rectangle` case to the `constructPath`
  command loop. Coords are `x, y, w, h`; only thin rectangles (`|h| <= 3`)
  become rules, so table cells and panels stay out. Kept the standalone
  `OPS.rectangle` branch as a documented fallback for a pdf.js version bump.
  Measured before/after: **0 blanks → 2** on a hand-built `re` document.
- **New fixture `tools/fixture-rect.pdf`** plus `tools/check-detection.mjs`,
  which asserts 8 behaviours including the negative cases. `fixture-underline`
  did NOT cover this — pdf-lib emits moveTo/lineTo, which is a different branch.
  That is why the bug survived a green test suite.
- **`hasPrintedDots()` / `shouldClearDots()`** exported from `fill.js` so the
  fields table and the writer share one predicate. `mixed` regions now clear.
- **Company hint** now requires `!b.label`. Verified: "Jawatan" stays `ignore`.
- **`NotReadableError`** — found only by driving a real browser. `app.js` cleared
  the file input immediately after calling the async `handleFile`, releasing the
  File's backing store while `arrayBuffer()` was in flight. Now awaited first.
  The headless harness and two full read-throughs had both missed it.
- **Settings** — debounced 250 ms, flushed on `pagehide`, quota failure shows a
  banner, scans over 1.5 MB refused up front. `resetBtn` cancels the pending
  write so it cannot land after the keys are removed.
- **`resetDocumentState()`** runs on Remove and before each new analysis;
  preview renders queue instead of being dropped.
- **Functions** — `nosniff` + `referrer-policy` repeated on Function responses
  (`public/_headers` does not cover them). Verified via `wrangler pages dev`:
  `/` and `/api/config` 401 unauthenticated, 200 authenticated, headers present.
- **Preview/annotation question settled**: `annotationMode: DISABLE` genuinely
  works. DISABLE vs ENABLE renders of the real template differ by ~36k pixels;
  with DISABLE the annotation values vanish while the genuinely printed company
  name stays. Earlier suspicion that the preview leaked stale values was a
  misreading of a low-resolution screenshot.
- **git initialised** (`main`, one initial commit, repo-local identity). Found
  that `.gitignore`'s `node_modules/` did not match the sandbox *symlink* — the
  pattern is now `node_modules` without the trailing slash.

Note for the browser tooling: `agent-browser errors` did not clear with
`--clear` and its list survived `close --all` within one CLI session, which made
a fixed bug look live. Confirm the list is empty on a fresh session *before*
interacting. Also: the sandbox sets `HTTP_PROXY`, so `curl` to 127.0.0.1 needs
`--noproxy '*'`.

## Real company stamp bundled as the default (same day, evening)

The user supplied `~/Downloads/logo-circle.png` and said "use this for company
stamp". It turned out to be a **complete stamp** — ring text
`EDGE INTELLIGENCE SDN. BHD.`, centre lines `202301036017` / `(1529940-V)`, star
— i.e. the same design `lib/stamp.js` generates. So it became the default
source rather than a second option.

- Installed as `public/stamp/company-stamp.png`, **cropped to its ink bounding
  box**. The original was 513×487 with the circle only 454×453 (88.5% of the
  width); sizing is driven off the frame, so the padding would have printed the
  stamp ~7% small. `alpha > 8` bbox + 2px pad → 461×460, aspect 1.0022.
- Stamp control is now three-way: `logo` (default) | `generated` | `upload`.
  The size slider was hoisted out of the generated panel — all three use it.
- Legacy `stampMode: 'image'` migrates to `'upload'` in `loadSettings`;
  unrecognised values fall back to the default (otherwise every panel is hidden,
  because `setStampMode` has no branch for them).
- The artwork is fetched at boot and held in memory, **never in localStorage**.
  Measured after a full session: settings storage stays at 314 bytes.

### The sizing bug this exposed

`drawStamp` had two independent size formulas. Generated: radius `size * 4.33`
→ diameter 8.66em. Image: `targetH = size * 4.6` → **barely half**. An uploaded
scan printed at ~53% of a generated stamp. Both now read one exported constant,
`STAMP_DIAMETER_EM = 8.66`, and share a centre (`cy = baseline + size * 0.35`).

Measured on an isolated blank page: generated **105.12pt**, artwork **102.96pt**,
centres identical (`dx = dy = 0.00`). The residual ~2% is the ring's own stroke
(`borderWidth = r * 0.020` stroked *on* the radius, so half falls outside) plus
anti-aliasing on the artwork edge — not a sizing error. Do not "correct" it.

### Measurement methodology (important)

Measuring the stamp on the real template is **useless**: the template's printed
text sits inside the same window, so the ink bbox just measures the template. A
first attempt with a thresholded diff saturated the entire window and looked
like a clean 0.0pt delta — a false pass. The working approach is
`tools/stamp-compare.mjs` writing an **isolated** page (blank Letter page, one
hand-made stamp blank) so the only ink is the stamp, then
`tools/stamp-render.py` measuring it.

### Browser tooling notes added this session

- `agent-browser set credentials <user> <pass>` — it is a `set` subcommand, not
  a top-level `credentials` command. Needed for the Basic-auth gate.
- `agent-browser eval` shares one persistent context, so `const o` from an
  earlier call throws "already been declared". Wrap each snippet in an IIFE.
  The context *is* the page's main world (a `window.confirm` override there does
  take effect).
- `agent-browser click` clicks by coordinates: a button below the fold silently
  misses (the click event never fires). `scrollintoview` first. This produced a
  false "the fill button does nothing" result.
- `agent-browser download <sel> <path>` intermittently hangs and gets SIGTERM'd;
  clicking and reading `#fillStatus` is the reliable check.
- `wrangler pages dev` **snapshots `public/` at startup** — deleting a file from
  disk afterwards does not change what it serves. To test a missing asset,
  restart the server, or intercept the request with `network route <full-url>
  --abort` on a cold cache (a `**/` glob pattern did not match).


## Stop clearing the dotted line (same day, later)

The user looked at a filled PDF and said the dotted leader was gone. They were
right: `clearDots` in `lib/fill.js` painted a white rectangle across the full
width of every `dots`/`mixed` blank before writing the typed value, which
erased the entire dot row, not just the dots under the text. They chose "no
clear at all" when offered the alternatives.

Changes:
- `lib/fill.js` — removed `clearDots` and the blanket call, removed
  `shouldClearDots`. The text branch now writes directly with no white-out.
  Signature/stamp paths unchanged (their ink already covers the dots under it;
  the dots on either side stay).
- `app.js` renderFields — dropped the Clear column (was a per-row checkbox that
  did nothing once clearing was gone) and the `hasPrintedDots` import.
- `index.html` — table head no longer has the `<th class="ta-c">Clear</th>`.
- `tools/check-detection.mjs` — the "merged region is reported as clearable"
  assertion was rewritten as "merged region is classified `mixed`" and
  "hasPrintedDots still flags it", since the predicate still exists for kind
  classification but the writer no longer acts on it.

Verified: check-detection 8/8, check-ui-refs 6/6, all four fixtures
unchanged. Re-rendered the Nama line at 260 dpi and the dots are back on
every row — they sit visibly under and around the typed values, exactly as a
hand-filled form looks. See `tools/dots-before.png` (previous build, all
dots gone) and `tools/dots-fixed.png` (current build, dots preserved).
